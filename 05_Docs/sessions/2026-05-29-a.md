## Goal
Investigate whether the ScreenshotFromVideos WebP plan can be adapted for REAL WebP export support in CropBatch, then write a CB-specific implementation plan.

## Findings (recon)
| Area | Finding |
|------|---------|
| Write paths | TWO broken functions: `ImageCropService.save()` (UTType-based, backs batch/rename/save-in-place/CLI/folder-watcher) AND `encode()` (backs Quick Export, `ThumbnailStripView:475`) — 6 flows total |
| CLI gap | `CLIHandler --format` parser (lines 87-94) has no `webp` case — can't even select WebP via CLI today |
| UI | TWO parallel format/quality UIs (`QualityResizeView` sidebar + legacy `ExportSettingsView`) — both need the Lossless toggle + Quality↔Effort label flip |
| Model | `lossless` must be threaded explicitly (`save()` UTType carries no quality/lossless metadata); `ExportSettingsCodable` needs Optional `lossless: Bool?` for profile backward-compat |
| Library | SDWebImageWebPCoder 0.15.0 latest; pulls SDWebImage + libwebp (pure-source, ~2-4 MB, notarization-clean, no `cs.*` entitlement) |
| SFV correction | "method=6 closes the cwebp gap (issue #116)" is only partially true — #116 is about *lossless*; both library and cwebp default to method=4. method=6 kept as absolute-quality choice, made a tunable constant |
| Project | Hand-managed `.xcodeproj` (no xcodegen); Sparkle already SPM-wired; adding the package is an interactive Xcode step Claude can't do headlessly |

## Decisions
- Use SDWebImageWebPCoder 0.15.0 via SPM (Option A), accepting ~2-4 MB; logged libwebp-direct bridge as future-shrink fallback
- Call `SDImageWebPCoder.shared.encodedData(...)` directly — do NOT register with `SDImageCodersManager` (encode-only usage, avoids launch side effect)
- Convert to sRGB before encode (color consistency with PNG/JPG/HEIC paths)
- `@preconcurrency import` both modules, confined to new `WebPEncoder.swift`
- `method=6` as a single tunable constant (drop to 4 if large-batch encoding is slow)
- Keep WebP+corner-radius forcing PNG for now (out of scope)
